1. Overall design / architecture
- The graphics are mainly handled by the GPU
- The screen uses double buffering at frame level
- Two complete render frames are used:
    an active frame (presented)
    an inactive frame (being built)
- Each frame holds several RenderLayers in Z order (e.g. background, sprites, text, UI)
- ActiveFrame points to the current render frame
- InactiveFrame points to the frame being written to
- All drawing operations always happen on the inactive frame
- Frames are switched by swapping pointers, no pixel copying
- Any CPU rendering is only used for debugging, measuring or statistics

2. Important requirements and limits
- Use real pointers (unsafe) where it is justified
- Plot() and all drawing functions always write to the inactive frame
- SwapBuffers() only switches frame references, never contents
- No individual layer may swap itself
- Premultiplied alpha is used consistently in GPU rendering
- The architecture must work with both:
    GPU rendering (the main case)
    CPU rendering (fallback / debug)

3. Decisions already made
- The screen owns the double buffering (not the render layers)
- Two lists are used for frames:
    FrameA
    FrameB
- A bool (or equivalent) decides which frame is active
- A RenderLayer represents a Z-ordered render plane, not a buffer
- No bitmap or pixel copies when switching frames
- Premultiplied alpha is used in all GPU layers
- All background calculations happen on the inactive frame

4. Latest changes / open problems
- The new SwapBuffers() implementation is tested and works correctly with GPU layers
- The CPU-based VBL load counter needs adapting to the GPU pipeline
- New drawing functions must strictly follow:
    build on inactive frame
    present active frame
- The terminology is being consolidated:
    Frame = buffer level
    RenderLayer = Z order level
…
