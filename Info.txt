How the game screen works (notes for working on the engine)
For the whole program - threads, the interpreter, sound, editors - see Documentation/Architecture.md.

1. Layers
- The screen is a list of GpuLayers in Z order (AmosGraphics._layers, also called ActiveFrame).
  Layer 0 is at the back; SCREEN SELECT n draws on layer n and creates it if needed.
- Each layer has one WriteableBitmap at the game's resolution (e.g. 640x480). There is no
  second buffer: PLOT, BAR, CIRCLE, PRINTG, TILE DRAW ... write straight into that bitmap on
  the BASIC thread, with unsafe pointers where it pays off.
- Per layer there are also shader values (ShaderValues: scroll position in [0], raster bars,
  weather and other effect parameters), opacity and fades.
- Sprites, bobs and FONT PRINT texts are not drawn into the bitmaps; they are kept as lists and
  drawn on top of their layer every time the screen is drawn.
- Pixels with the colour 0,0,0 are transparent. Premultiplied alpha is used throughout.

2. Drawing the screen (render thread)
- AmosGpuView.Render collects the layers, sprites and texts and hands ScreenDrawOperation to
  Avalonia. On the render thread each layer is drawn at the game's resolution through its
  shader (Shaders.cs, SKRuntimeEffect), and the finished picture is scaled up to the window
  once: by whole pixels first, then smoothly the rest of the way ("sharp bilinear"), or
  through the CRT effect (F8).

3. Frames: WAIT VBL
- WAIT VBL ends a frame. It steps fades, animations and sprite effects, presents the frame
  (PresentFrame takes a snapshot of the sprites, the FONT PRINT texts, every layer's shader
  values and which layers are on), and then waits for the screen refresh that shows it
  (DisplayClock). Presenting first means the refresh always shows the frame just finished.
- DisplayClock: the game window reports each screen refresh (RequestAnimationFrame) and WAIT
  VBL waits for those, 60 frames a second: every refresh at 60 Hz, every second at 120 Hz, an
  average of 60 at other rates, and a timer when no window is refreshing (tests, hidden window).
- At each refresh, before WAIT VBL lets the program go on, the view locks in the latest
  presented frame (LatchShownFrame), and that is what is drawn. Without it the screen was drawn
  in a race with the BASIC thread and the picture now and then stood still or jumped a frame.
- Programs without WAIT VBL are drawn from the live state.
- The bitmaps themselves are not part of the snapshot. A program that redraws a whole layer
  every frame and must never show it half-drawn uses two layers and shows one while drawing
  the other (see Frog Hop).

4. Measuring
- The game window title shows FPS, BASIC (share of time the program works between WAIT VBLs),
  CPU (the whole app's CPU time, 100 % = one core, like Activity Monitor) and SYNC (the refresh rate WAIT VBL follows, or "timer").
- AMOS_FRAMELOG=frames.csv logs every refresh, WAIT VBL and draw with its time (FrameLog.cs):
    AMOS_FRAMELOG=frames.csv dotnet run -- --play Projects/parallax_layers.amosproj
